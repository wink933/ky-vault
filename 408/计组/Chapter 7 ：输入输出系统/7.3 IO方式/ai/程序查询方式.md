### 结论

**程序查询方式**是一种最基础的 I/O 控制方式，指主机与外设之间的数据交换完全由 **CPU 通过执行程序（代码）来控制和实现**。 它的核心特征是：CPU 启动外设后，会不断循环读取 I/O 接口的状态字，直到外设准备就绪才进行一次数据交换。本质上是一种**“踏步等待”**机制。

---

### 关键点

根据 408 大纲，程序查询方式的执行流程与特点主要总结为以下 4 条：

1. **核心机制（工作流程）**
    - CPU 发出 I/O 启动指令给外设。
    - CPU 不断循环读取并测试 I/O 接口中的**状态寄存器**。
    - 如果状态为“未就绪”，CPU 就一直在循环中死等（踏步等待）。
    - 一旦状态变为“就绪”，CPU 便通过数据总线完成一次数据的读/写操作。
    - 修改内存地址和计数值，判断传输是否结束。
2. **两种查询策略**
    - **独占查询**：CPU 一旦启动外设，就 100% 占用自身时间死死盯着状态端口，此时 CPU 与外设完全**串行工作**。
    - **定时查询**：CPU 周期性地（每隔一段时间）暂停当前任务，去查询一下外设状态，若没就绪就先回去干别的。
3. **性能影响（优缺点）**
    - **优点**：硬件控制逻辑极度简单，接口设计成本最低（不需要中断硬件和 DMA 控制器）。
    - **缺点**：CPU 大量时间被浪费在无意义的查询循环上，**CPU 利用率极低**。同时系统无法及时响应外设的突发事件。
4. **适用场景** 通常只适用于工作速度要求不高、外设数量少、对实时性无要求的简单微型计算机系统。

### 易错点 / 易混点（⚠️ 408 极高频陷阱）

针对 I/O 方式的选择题，这里是重灾区：

- ❌ **常见陷阱 1：认为“程序查询方式不需要占用系统总线，只是 CPU 在内部死等”。**
    - ✅ **408 纠正**：**大错特错！** CPU 所谓的“死等查询”，本质上是不断地执行 `IN` 指令去读取 I/O 接口的状态寄存器。每一次读取，**都会向地址总线发地址，并在“数据总线”上取回状态字**。频繁的查询不仅浪费 CPU，还会疯狂抢占系统总线的带宽。
- ❌ **常见陷阱 2：混淆“程序查询”和“程序中断”在【数据传输环节】的区别。**
    - ✅ **408 纠正**：很多人以为只有程序查询是 CPU 传数据，中断不是。其实在 408 中必须牢记：**无论是程序查询还是程序中断，其【真正的数据搬运】都是由 CPU 亲自执行指令（`IN/OUT`、`LOAD/STORE`）来完成的，数据必须经过 CPU 内部的寄存器中转！** 两者的唯一区别只是“CPU 是一直死等外设就绪，还是外设就绪了再打断 CPU”。只有 DMA 方式才是绕过 CPU 直接传数据。
- ❌ **易混概念：“就绪”状态的方向性问题。**
    - ✅ **提醒**：对于输入设备（如键盘），“就绪”代表数据已经装进接口，CPU 可以来**读**了；对于输出设备（如打印机），“就绪”代表接口空闲了，CPU 可以往里面**写**新数据了。

**程序查询方式 = “老板（CPU）全职亲自盯梢”**

- **启动** = 老板对车间工人（外设）喊：“开始印材料！”
- **循环查询** = 老板什么活都不干了，就搬个板凳坐在车间门口，每秒钟问一次：“印完没？”、“印完没？”（**浪费 CPU 和总线带宽**）。
- **数据交换** = 工人终于说“印完了”，老板亲手把材料抱回办公室库房（**CPU 亲自执行数据传送**）。
