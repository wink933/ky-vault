在 408 考纲的“进程管理”章节中，**TS 指令（TestAndSet，测试并设置指令）** 与 **Swap 指令（XCHG，交换指令）** 是通过**硬件机制**实现进程互斥的两种经典硬件原子指令。它们均从硬件底层保证了“检查”与“加锁”操作的不可分割性。

以下为你硬核拆解这两条指令的底层逻辑、代码实现与对比：

### 结论

**TS 指令**与 **Swap 指令**在功能与效果上是完全等价的：它们都是依靠硬件逻辑保证执行过程不被中断的**原子操作指令**，核心思想都是“通过一次不可分割的操作，读取锁的状态并同时将锁置为占用状态”。两者的本质区别仅在于**底层硬件逻辑的物理动作不同**——TS 指令是直接“读旧值并赋新值”，而 Swap 指令是“交换两个变量（寄存器与内存）的值”。

---

### 关键机制

#### 1. 核心维度严格对比

| **维度**      | **TS 指令 (TestAndSet)**                                    | **Swap 指令 (Exchange/XCHG)**                                          |
| :---------- | :-------------------------------------------------------- | :------------------------------------------------------------------- |
| **底层硬件动作**  | 读取指定地址的旧值，并将其设置为 `true`                                   | 交换两个变量（如内存锁与寄存器）的值                                                   |
| **临界区实现逻辑** | 将全局锁 `lock` 的旧值读入并同时将 `lock` 改为 `true`；若旧值为 `false`，则成功进锁 | 进程先将局部变量 `key` 设为 `true`，再与全局锁 `lock` 交换；若交换后 `key` 变为 `false`，则成功进锁 |
| **原子性保障**   | 由硬件电路/锁总线保证“读”与“写”连贯执行                                    | 由硬件电路/锁总线保证“交换”过程不可被打断                                               |
| **遵循的互斥原则** | 满足“空闲让进”、“忙则等待”、“有限等待”                                    | 满足“空闲让进”、“忙则等待”、“有限等待”                                               |
| **违背的互斥原则** | **违背“让权等待”**（会导致忙等待/自旋）                                   | **违背“让权等待”**（会导致忙等待/自旋）                                              |
| **适用场景**    | 适用于多处理机（SMP）及单处理机环境                                       | 适用于多处理机（SMP）及单处理机环境                                                  |

### 易错/易混点

针对 408 统考真题选择题极其喜欢挖坑的逻辑陷阱（如 2016、2018 统考题），请务必保持绝对清醒：

- **陷阱 1：TS 指令与 Swap 指令能实现“让权等待”吗？（极高频致死考点！）**
    - **辨析：绝对不能！** 当进程无法进入临界区时，两条指令都会让进程在 `while` 循环中**持续执行循环检查（忙等待 / 自旋锁 Spinlock）**，这会白白浪费 CPU 时间片。要实现真正意义上的“让权等待”，必须引入信号量机制中的阻塞队列（`block()` 原语）。
- **陷阱 2：使用 Swap 指令时，局部变量 `key` 的初始值设置错误会引发什么？**
    - **辨析：** 每次尝试进入临界区前，进程必须将自己的局部变量 `key` **重新初始化为 `true`**。如果忘记初始化或设为 `false`，则无法正确反映锁的前一个状态，可能导致多个进程同时进入临界区，破坏互斥逻辑。
- **陷阱 3：TS/Swap 指令能完全避免死锁或饥饿吗？**
    - **辨析：不能避免饥饿！** 由于硬件指令在挑选下一个获得锁的进程时没有任何优先级或队列顺序（即哪个进程先抢到总线/内存访存权谁就拿锁），可能导致某些幸运进程反复进锁，而某些不幸运的进程长期抢不到锁，从而引发**“饥饿”现象**。

### 代码伪代码与推导对比

为了在大题分析中规范表达，请熟记两者的伪代码逻辑结构（408 答题标准）：

#### 1. TS 指令的逻辑实现与使用

```
// TS 指令的硬件功能描述（硬件原子执行，不可打断）
boolean TestAndSet(boolean *lock) {
    boolean old = *lock;  // 1. 读取旧值
    *lock = true;         // 2. 将锁置为已占用
    return old;           // 3. 返回旧值
}

// 进程进入与退出临界区的代码结构
while (TestAndSet(&lock)); // 尝试加锁：若旧值 lock 为 true，则循环忙等；若为 false，则返回 false 退出循环并已成功把 lock 设为 true
// ----------- 临界区 (Critical Section) -----------
lock = false;              // 解锁：释放资源
// ----------- 剩余区 (Remainder Section) -----------
```

#### 2. Swap 指令的逻辑实现与使用

```
// Swap 指令的硬件功能描述（硬件原子执行，不可打断）
void Swap(boolean *a, boolean *b) {
    boolean temp = *a;
    *a = *b;
    *b = temp;
}

// 进程进入与退出临界区的代码结构
boolean key = true;        // 局部变量 key 初始化为 true
while (key == true) {
    Swap(&lock, &key);    // 交换 lock 和 key：若原 lock 为 false，则交换后 key 变为 false，退出循环
}
// ----------- 临界区 (Critical Section) -----------
lock = false;              // 解锁：释放资源
// ----------- 剩余区 (Remainder Section) -----------
```
