## 哲学家进餐问题

**问题描述：**

一张圆桌旁围坐 5 名哲学家，每两名相邻哲学家之间放置一根筷子，共 5 根筷子，每位哲学家面前有一碗米饭，如图 2.13 所示。哲学家交替进行思考与进餐：思考时互不影响；饥饿时，必须同时持有左右两根筷子才能开始进餐（筷子需要逐根拿起）；若所需筷子已被他人持有，则必须等待；进餐结束后，立即放下两根筷子，继续思考。

**问题分析：**

1. 关系分析。每根筷子被其两侧的哲学家共享，因此对同一根筷子的访问必须互斥。
    
2. 整理思路。共有 5 个并发进程。本题的关键是如何让一名哲学家安全地获取左右两根筷子，避免死锁或饥饿。直观的解决思路有两种：① 尝试同时获取两根筷子，即仅当左右筷子均空闲时才拿起；② 对哲学家的行为制定规则，破坏死锁产生的必要条件。
    
3. 信号量设置。定义互斥信号量数组 `chopstick[5]`，控制对 5 根筷子的互斥访问，初值均为 1。哲学家编号为 0~4，哲学家 $i$ 左侧筷子的编号为 $i$，右侧筷子的编号为 $(i+1)\%5$。
    

一个直观的实现如下（存在死锁风险）：



```c
semaphore chopstick[5]={1,1,1,1,1}; //初始化 5 根筷子的信号量
Pi() {                              //i 号哲学家进程
    do {
        P(chopstick[i]);            //拿起左侧筷子
        P(chopstick[(i+1)%5]);      //拿起右侧筷子
        进餐
        V(chopstick[i]);            //放回左侧筷子
        V(chopstick[(i+1)%5]);      //放回右侧筷子
        思考
    } while(1);
}
```

假设 5 名哲学家同时饥饿，并几乎同时执行完 `P(chopstick[i])`。此时，每位哲学家各持一根左侧筷子，且均在等待右侧筷子，系统进入循环等待状态，所有进程阻塞，形成死锁。

为防止死锁发生，可对哲学家进程施加一些限制条件：① 限制最多 4 名哲学家同时尝试进餐，确保至少有一人能获得两根筷子，这样在其用餐完毕后释放他的两根筷子，从而使更多的哲学家能够进餐；② 对哲学家编号，规定奇数号哲学家先拿左筷、再拿右筷，偶数号则相反，打破循环等待条件；③ 仅当左右两根筷子均空闲时，才允许哲学家同时拿起。

假设采用第二种方法，当一名哲学家左右两侧的筷子都可用时，才允许他拿起筷子。


```c
semaphore chopstick[5]={1,1,1,1,1}; //初始化 5 根筷子的信号量
semaphore mutex=1;                  //设置取筷子的信号量
Pi() {                              //i 号哲学家的进程
    do {
        P(mutex);                   //申请取筷子的信号量
        P(chopstick[i]);            //拿起左侧筷子
        P(chopstick[(i+1)%5]);      //拿起右侧筷子
        V(mutex);                   //释放取筷子的信号量
        进餐
        V(chopstick[i]);            //放回左侧筷子
        V(chopstick[(i+1)%5]);      //放回右侧筷子
        思考
    } while(1);
}
```

哲学家进餐问题是经典的进程同步案例，其本质在于预防循环等待。尽管大部分习题和真题通过消费者-生产者模型或读者-写者问题就能求解，但对哲学家进餐问题仍然要熟悉。考研复习的关键在于反复多次和全面，“偷工减料”是要吃亏的。


### 结论

哲学家进餐问题（Dining Philosophers Problem）是操作系统中用于测试和演示**并发控制与死锁避免**的最经典模型。它的核心难点在于：系统中有多个并发进程（哲学家）竞争多个共享临界资源（筷子），如果分配策略不当，极易引发所有进程都在等待他人释放资源而无限期僵持的**死锁（Deadlock）**现象。

### 关键机制

- **物理模型：** 一张圆桌坐着 5 名哲学家，每两名哲学家之间放着 1 根筷子（共 5 根）。哲学家只交替进行“思考”和“进餐”两种动作。
- **资源限制：** 哲学家必须**同时拿到左右两根筷子**才能进餐。进餐完毕后，会同时放下两根筷子。
- **信号量定义：**
    - 通常定义一个信号量数组 `semaphore chopstick = {1, 1, 1, 1, 1};`，这里的每一根筷子都是一个**互斥信号量**（初值为 1），表示每次只能被一名哲学家占用。

### 动态执行过程与死锁危机

如果采用最直观的“先拿左手，再拿右手”策略，其动态执行步骤如下：

1. **思考：** 哲学家在独立思考，不占用任何资源。
2. **申请左筷子：** 哲学家饿了，执行 `P(chopstick[i]);` 获取左手边的筷子。
3. **申请右筷子：** 哲学家接着执行 `P(chopstick[(i+1)%5]);` 获取右手边的筷子。
4. **进餐：** 成功拿到两根筷子，开始进餐。
5. **归还资源：** 进餐完毕，执行 `V` 操作同时放下左右筷子。

**🔴 死锁触发图景：** 假设在某一个极端时刻，5 名哲学家**同时**感到饥饿，并且**同时**执行了步骤 2（拿起了左手的筷子）。此时，5 根筷子的信号量全被消耗为 0。当他们推进到步骤 3 准备拿右手筷子时，发现全被相邻的哲学家占用，于是 5 个人全部陷入阻塞态。这就是典型的**环路等待**，死锁由此发生。

### 解决方案与典型伪代码示例

为了打破上述死锁，408 考纲中规定了三种标准的预防死锁策略。

#### 方案一：引入互斥锁（保护“拿筷子”的原子性）

**核心逻辑：** 增加一个互斥信号量 `mutex = 1`，规定哲学家在拿筷子前必须获得该锁，拿完两根筷子后再释放锁。这样可以保证同一时刻只有一个哲学家在请求筷子，破坏了死锁的发生条件。

```
semaphore chopstick = {1, 1, 1, 1, 1}; // 互斥信号量，代表5根筷子
semaphore mutex = 1;                       // 互斥信号量，用于互斥拿筷子的动作

Pi() {
    while(1) {
        思考;
        P(mutex);                 // 【核心】申请拿筷子的通行证
        P(chopstick[i]);          // 拿起左侧筷子
        P(chopstick[(i+1)%5]);    // 拿起右侧筷子
        V(mutex);                 // 【注意】拿到后立刻释放通行证，允许别人去拿

        进餐;

        V(chopstick[i]);          // 放回左侧筷子
        V(chopstick[(i+1)%5]);    // 放回右侧筷子
    }
}
```

#### 方案二：限制就餐人数（破坏系统满载）

**核心逻辑：** 5 根筷子，如果最多只允许 4 名哲学家同时去竞争，那么根据鸽巢原理，必然至少有 1 名哲学家能拿到 2 根筷子并进餐，从而打破死锁。

```
semaphore chopstick = {1, 1, 1, 1, 1};
semaphore count = 4; // 资源信号量，最多允许4个哲学家同时请求进餐

Pi() {
    while(1) {
        思考;
        P(count);                 // 请求进入就餐竞争队列
        P(chopstick[i]);          // 拿起左侧筷子
        P(chopstick[(i+1)%5]);    // 拿起右侧筷子

        进餐;

        V(chopstick[i]);          // 放回左侧筷子
        V(chopstick[(i+1)%5]);    // 放回右侧筷子
        V(count);                 // 退出竞争队列，让出名额
    }
}
```

_(注：第 3 种方案为**非对称策略**，即要求奇数号哲学家先拿左筷再拿右筷，偶数号哲学家先拿右筷再拿左筷，直接从空间上破坏环路等待。)_

### 易错/易混点

- **陷阱：互斥锁的作用域过大（极其高频的命题点）。**
    - **辨析：** 在方案一中，`V(mutex)` 必须紧跟在拿完两根筷子之后（进餐之前）。如果将代码写成 `P(mutex) -> 拿双筷 -> 进餐 -> 放双筷 -> V(mutex)`，虽然不会发生死锁，但**将导致 5 名哲学家彻底沦为串行进餐**（同一时刻只能有 1 人在吃饭）。而实际上，圆桌对面的两名哲学家（如 $P_0$ 和 $P_2$）在物理上是完全可以同时进餐的。锁住进餐过程会严重损毁系统的并发性能。
- **区分：资源瓶颈。** 哲学家进餐问题纯粹是资源的同级竞争（大家都在抢同一种东西），它不涉及“生产者-消费者”模型中严格的前后制约（同步）逻辑。因此代码中**通常只需要互斥操作**，而不需要设计像 `empty/full` 这样的同步信号量。
