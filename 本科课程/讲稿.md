## 第 2 页：背景与痛点思考 (引言区)

### 📊 幻灯片显示内容

**分布式 SpMV 面临的核心挑战**：

1. **负载不均衡 (Load Imbalance)**：稀疏矩阵的非零元分布极不规律，导致不同计算节点的计算量差异巨大。

2. **高昂的通信开销 (Communication Overhead)**：进程间需要频繁交换向量数据，网络通信成为性能瓶颈。

  

**论文原版干预策略**：

- 在计算与通信之间寻找极值点，提出了 **DistSpMV_Balanced** 算法。

  

### 🎤 演讲稿 (预计时长: 1.0 min)

“在正式进入代码复现前，我们先明确一下痛点。在分布式架构下做稀疏矩阵向量乘，我们最怕两件事：一是有的节点闲死、有的节点累死（也就是负载不均）；二是节点间为了交换数据，把时间全花在网络通信上了。

原论文《Balancing Computation and Communication》的核心思想，就是通过聪明的预处理，在‘计算绝对均衡’和‘零通信’之间找到一个平衡点，宁可稍微冗余一点计算，也要大幅度削减通信。”

## 第 3 页：论文复现一 —— 预处理与矩阵重排 (Pre-processing)

### 📊 幻灯片显示内容

**步骤 1：基于 METIS 的图划分与重排**

- **目标**：将非零元（NNZ）尽可能聚集到矩阵的对角块（Diagonal Blocks）。

- **作法**：将 CSR 格式矩阵对应的结构抽象为图，通过 Graph Partitioning 进行节点重新编号。

  

### 🧑‍💻 代码片段 (C++)

```cpp

// 核心逻辑演示：调用 METIS 划分并重排矩阵

idx_t n = num_rows;

idx_t nparts = num_mpi_tasks;

idx_t objval;

std::vector<idx_t> part(n);

  

// 1. 图划分：获得各行的归属

METIS_PartGraphKway(&n, &ncon, xadj, adjncy, NULL, NULL, NULL,

&nparts, NULL, NULL, options, &objval, part.data());

  

// 2. 矩阵重排 (Permutation) 使得非零元向对角线集中

MatrixPermutation(original_csr_matrix, part, reordered_csr_matrix);

```

  

### 🎤 演讲稿 (预计时长: 1.0 min)

“复现的第一步是预处理。大家看屏幕上的代码框。我们拿到原始的稀疏矩阵后，首先利用 METIS 库对其进行 K-way 图划分。为什么要重排？因为只有把非零元尽量集中在对角线上，各个 MPI 进程在计算自己的对角块时，才不需要去跟别人索要向量元素。这从根源上把后续的通信基数降了下来。”

## 第 4 页：论文复现二 —— 双层负载均衡策略 (核心算法)

### 📊 幻灯片显示内容

**核心逻辑：计算平衡 vs 通信平衡**

1. **计算局部性扩展 (Column Adjustment)**：

- 设定阈值 `lower_bound = max(NNZ in diagonal blocks)`。

- 主动向右扩展对角块，直到包含的 NNZ >= lower_bound。

- **结果释放**：矩阵撕裂为 `Local Matrix` (零通信) 和 `Remote Matrix` (需通信)。

2. **行数调整 (Row Adjustment)**：

- 根据 Remote Matrix 剩余的计算量，微调进程负责的行边界。

  

### 🧑‍💻 代码片段 (C++ 伪代码)

```cpp

// Algorithm 1: 扩展列边界，切分 Local 与 Remote 矩阵

int lower_bound = GetMaxNNZ_In_Diagonal(matrix, num_procs);

  

for (int p = 0; p < num_procs; p++) {

int current_nnz = matrix.DiagonalBlock[p].nnz;

int right_boundary = matrix.DiagonalBlock[p].end_col;

// 牺牲一点冗余局部存储，换取通信免除

while (current_nnz < lower_bound && right_boundary < total_cols) {

current_nnz += CountNNZ_in_Col(matrix, p, right_boundary);

right_boundary++;

}

matrix.Local[p] = ExtractLocal(matrix, p, right_boundary);

matrix.Remote[p] = ExtractRemote(matrix, p, right_boundary);

}

```

  

### 🎤 演讲稿 (预计时长: 1.5 min)

“这是这篇论文最精妙，也是我复现的重点部分。原论文提出，不要拘泥于完美的正方形对角块。我们算出所有块中最密集的那个作为 `lower_bound` 阈值。

然后对于那些稀疏的块，我们主动把它们的列边界向右扩展！

为什么扩展对角块？因为被划入 Local 矩阵的元素，计算时是不需要网络通信的。这种做法本质上是‘用内存换通信’——让每个进程多持有一点数据，硬生生把需要通过网络传输的 Remote Matrix 规模压缩到最小。”

## 第 5 页：论文复现三 —— MPI + OpenMP 混合并行执行

### 📊 幻灯片显示内容

**计算模式：分布式集群 + 多核节点**

- **通信**：`MPI_Alltoallv` 交换 Remote 矩阵所需的向量 x 元素。

- **计算**：多线程 `OpenMP` 负责单节点内的 CSR 矩阵相乘。

  

### 🧑‍💻 代码片段 (MPI + OpenMP)

```cpp

// 1. 发起通信获取 Remote 矩阵所需的向量元素

MPI_Alltoallv(send_buf, send_counts, send_displs, MPI_DOUBLE,

recv_buf, recv_counts, recv_displs, MPI_DOUBLE, MPI_COMM_WORLD);

  

// 2. Local 矩阵计算 (OpenMP 并行)

#pragma omp parallel for

for (int i = 0; i < local_rows; i++) {

double sum = 0;

for (int j = local_mat.row_ptr[i]; j < local_mat.row_ptr[i+1]; j++) {

sum += local_mat.values[j] * local_x[local_mat.col_idx[j]];

}

y[i] = sum;

}

// 3. Remote 矩阵计算 (伪代码同上，略)

```

  

### 🎤 演讲稿 (预计时长: 1.0 min)

“在具体的执行架构上，我采用了经典的 MPI + OpenMP 混合编程模型。节点间的 Remote 数据依赖通过 `MPI_Alltoallv` 统一交换。然后在节点内部，无论是 Local 计算还是 Remote 计算，都利用 `#pragma omp parallel for` 分配给多核 CPU 的不同线程。至此，我们已经严格、完整地复现了论文中的 DistSpMV_Balanced 算法。”

## 第 6 页：深入底层 —— 我们还能压榨出什么性能？

### 📊 幻灯片显示内容

**原论文算法的局限与现代硬件架构的脱节**：

1. **同步阻塞等待**：`MPI_Alltoallv` 是阻塞的，通信期间 CPU 竟然在“睡大觉”！

2. **算力闲置**：单纯的 OpenMP 循环无法自动利用 CPU 宽指令集（如 AVX2/AVX-512），算力利用率不足 10%。

3. **内存墙**：CSR 格式带来严重的随机内存跳跃，L3 Cache Miss 极高。

  

**我的三大优化破局点**：

🎯 计算-通信重叠 (Overlap)

🎯 SIMD 向量化 (Vectorization)

🎯 智能内存预取 (Smart Prefetching)

  

### 🎤 演讲稿 (预计时长: 1.0 min)

“在复现完毕后跑 Profile 的时候，我发现了一些严重的问题。原论文的提出具有时代局限性。第一，它用的是阻塞通信，网卡传数据的时候，强大的 CPU 竟然在一旁干等。第二，对现代处理器的向量单元和缓存层次毫无感知。因此，我基于现代微架构特点，为其量身定制了三个维度的深入优化方案。”

## 第 7 页：优化方案一 —— 通信与计算的深度重叠 (Overlap)

### 📊 幻灯片显示内容

**策略：用异步通信 (Non-blocking) 隐藏网络延迟**

- 舍弃 `MPI_Alltoallv`，化整为零改用 `MPI_Isend` / `MPI_Irecv`。

- 构建**流水线**：网卡搬运 Remote 数据的同时，CPU 全速计算 Local 数据。

  

### 🧑‍💻 代码片段 (优化前后对比)

```cpp

/* === 优化后的重排流水线架构 === */

MPI_Request reqs[num_requests];

  

// 1. 异步发起 Remote 数据请求

for (int i=0; i<neighbors; i++) {

MPI_Irecv(..., &reqs[recv_idx++]);

MPI_Isend(..., &reqs[send_idx++]);

}

  

// 2. CPU 不等待！立刻开始 Local 矩阵计算

Compute_SpMV_OpenMP(local_mat, local_x, y);

  

// 3. 阻塞点后移：等待 Remote 数据全部就绪

MPI_Waitall(num_requests, reqs, MPI_STATUSES_IGNORE);

  

// 4. 计算 Remote 矩阵并合并结果

Compute_SpMV_OpenMP(remote_mat, recv_buf, y);

```

  

### 🎤 演讲稿 (预计时长: 1.5 min)

“这是第一个优化点也是收效最立竿见影的。请看右侧的代码对比。我不仅把阻塞式的通信改为了异步的 `Isend/Irecv`，更重要的是进行了逻辑流水线的重组：在发起网络数据请求后，CPU 立刻掉头去算本地的 Local Matrix。由于预处理时 Local 矩阵占据了绝大多数非零元，这段漫长的本地计算时间，完美地掩盖了网络的延迟（把 Network Latency 给藏起来了）。最后只要做一个 Wait 同步，再算 Remote 的尾巴即可。”

## 第 8 页：优化方案二 —— 内存对齐与 SIMD 向量化

### 📊 幻灯片显示内容

**策略：唤醒沉睡的 AVX-512 / AVX2 算力**

- **内存对齐**：使用 `posix_memalign` 分配 CSR 数组，确保在 64 字节边界对齐。

- **SIMD 指令介入**：强转编译器生成宽向量并行计算汇编代码。

  

### 🧑‍💻 代码片段 (C++ & OpenMP SIMD)

```cpp

// 优化不仅在算法，更在微架构

// 确保指针内存是对齐的，避免跨 Cacheline 惩罚

double* aligned_values = (double*) _mm_malloc(nnz * sizeof(double), 64);

  

#pragma omp parallel for schedule(dynamic, 64)

for (int i = 0; i < local_rows; i++) {

double sum = 0.0;

// 强制编译器生成 AVX 向量化指令，一次处理 4/8 个 double

#pragma omp simd reduction(+:sum) aligned(aligned_values: 64)

for (int j = row_ptr[i]; j < row_ptr[i+1]; j++) {

sum += aligned_values[j] * x[col_idx[j]];

}

y[i] = sum;

}

```

  

### 🎤 演讲稿 (预计时长: 1.0 min)

“现代处理器的核心算力都在 SIMD 单元里。在进行矩阵乘法最内层循环时，我加入了 `#pragma omp simd` 辅以 reduction 归约。但光写指令没用，如果内存不对齐，强行并发会引发异常或性能惩罚。为此，我重构了存储结构，使用 64 字节强制对齐向量。现在，CPU 一个时钟周期可以直接吞下 4 到 8 个浮点数操作，计算吞吐量呈倍数翻涨。”

## 第 9 页：优化方案三 —— 突破内存墙：智能硬件预取 (Smart Prefetching)

### 📊 幻灯片显示内容

**策略：缓解 CSR 格式固有的随机访存劣势**

- **问题**：`x[col_idx[j]]` 意味着下一次访问的内存地址是不可预测的。

- **解法**：提前 2-4 个迭代步长（Stride），强制将指针数据送入 L1 Cache。

  

### 🧑‍💻 代码片段 (GCC/Clang 内置指令)

```cpp

for (int i = 0; i < local_rows; i++) {

double sum = 0;

for (int j = row_ptr[i]; j < row_ptr[i+1]; j++) {

// 软硬件结合：提前预取未来的随机列索引数据到 L1 缓存

// 0: 准备读操作 (Read)

// 3: 最高时间局部性保存，保留入各级缓存 (Keep in cache)

__builtin_prefetch(&x[col_idx[j + 4]], 0, 3);

sum += values[j] * x[col_idx[j]];

}

y[i] = sum;

}

```

  

### 🎤 演讲稿 (预计时长: 1.0 min)

“评委老师们，众所周知，做稀疏矩阵实际上是在做访存。`x[col_idx[j]]` 这样的间接寻址非常伤 Cache！硬件预取器遇到这种随机跳跃往往会失效。因此我加入了 Software Prefetching，用编译器内置的 `__builtin_prefetch` 宏。在计算当前行数据时，我就向 CPU 发送指令，去通知 L3 Cache 提前把后验 4 个步长外的向量拉到速度最快的 L1 Cache 里等着。这一举措极大平滑了流水线的气泡。”
