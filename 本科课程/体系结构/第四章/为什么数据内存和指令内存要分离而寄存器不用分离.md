**数据内存（Cache）必须分离，而寄存器不用分离，根本原因在于它们在流水线中所处的物理阶段不同、存储的内容不同，以及硬件实现“多端口”的物理成本有着天壤之别。**

我们可以从以下三个核心维度来深度拆解这个架构设计：

### 1. 存储内容的本质区别

- **内存/Cache 既存指令又存数据**：在冯·诺依曼架构下，程序代码（指令）和程序运行所需的数据最初都混存在同一片主存中。因此，在缓存层面，CPU 必须同时拉取指令和数据。
- **通用寄存器（GPR）根本不存指令**：寄存器堆是专门为 CPU 运算提供“原材料”的。**指令在取指阶段（IF）被取出后，是直接存放在对程序员透明的“指令寄存器（IR）”或流水线锁存器中的**，根本不会被放进那 32 个通用寄存器里。既然通用寄存器里只有数据，自然就不存在“分离指令寄存器和数据寄存器”的需求。

### 2. 流水线阶段的“结构冒险”与端口冲突

在经典的 5 级流水线中，冲突的焦点完全不同：

- **Cache 的致命冲突（IF vs MEM）**：流水线的 **取指阶段（IF）** 需要不断从内存读取指令，而 **访存阶段（MEM）** 需要读写内存中的数据。在同一个时钟周期内，这两条不同的指令会同时向缓存发起请求。如果采用统一缓存且只有一个端口，就会发生严重的 **结构冒险（Structural Hazard）**，导致流水线被迫停顿。
- **寄存器的错峰访问（ID vs WB）**：通用寄存器的访问发生在 **译码/读寄存器阶段（ID）** 和 **写回阶段（WB）**。虽然 ID 和 WB 也可能在同一个时钟周期内发生碰撞，但体系结构通过两种低成本手段完美解决了这个问题：
    1. 正如我们在之前时空图推演中提到的，硬件采用了 **“前半周期写回，后半周期读取”** 的内部节拍设计，天然错开了冲突。
    2. 增加独立的读写端口（下文详述）。

### 3. 硬件“多端口”的物理代价差异极大

要解决同一个周期内两个部件抢夺同一个资源的结构冒险，最直接的暴力解法就是 **“增加硬件资源（增加端口）”**。

- **为什么寄存器可以加端口？** 通用寄存器堆容量极小（通常只有 32 个或 64 个字），物理面积很小。因此，架构师可以轻松地为寄存器堆设计 **多端口（Multi-port）**。例如在超标量或乱序执行处理器中，寄存器文件通常被设计为具有 $2x$ 个读端口和 $x$ 个写端口。有了独立的多端口，ID 段和 WB 段就可以同时读写不同的寄存器而互不干扰。
- **为什么 Cache 不能加端口？** L1 Cache 容量很大（通常为 32KB 到 192KB 不等），由海量的 SRAM 单元构成。如果为这么大的存储阵列设计支持“同时读写”的真双端口（Dual-port），会使得芯片面积和功耗呈指数级暴增，并且极大地拖慢命中时间（Hit Time）。
- **终极折中方案**：既然造双端口的大容量 Cache 太贵又太慢，架构师就直接把 L1 Cache 从物理上一切为二，切分成一个 **L1 指令缓存（L1-I）** 和一个 **L1 数据缓存（L1-D）**。这也就是所谓的 **哈佛架构（Harvard Architecture）**，它用最经济的方式变相实现了“双端口”，完美消除了取指和访存的结构冒险。

**💡 补充延伸：寄存器其实也有“分离”** 虽然寄存器不分“指令和数据”，但在现代处理器中，寄存器确实会按 **数据类型** 进行分离。例如，绝大多数架构（如 SPARC、MIPS、RISC-V）都会在物理上分离出独立的 **整型寄存器堆（Integer Registers）** 和 **浮点寄存器堆（FP Registers）**。这也是为了增加并发端口带宽，避免整数运算和浮点运算在同一个周期争抢读写端口。
