## 1. 遇难者：`"encoding/json"` (JSON 序列化工具)

在单机 C++ 游戏开发中，如果你要在内存里传递一个结构体（比如玩家的坐标、动作），直接传指针或引用就行了。但在网络中，数据必须变成**扁平的字节流 (Byte Stream)**。

- **在 C++ 中**：标准库里没有现成的 JSON 库，你通常需要引入第三方库（比如 `nlohmann/json` 或者腾讯的 `RapidJSON`）。
    
- **在 Go 中**：`"encoding/json"` 是官方自带的强力武器。它可以极其方便地把一个 Go 结构体（`struct`）打包成一串 JSON 格式的字节，或者把接收到的字节重新组装成结构体。
    
- **灾难隐患**：JSON 的致命弱点在于，**它只用大括号 `{}` 来表示对象的开始和结束，并没有在最前面告诉你这个包总共有多少个字节**。当底层 TCP 把三个 `{...}` 粘连在一起变成一个长字符串时，`json.Unmarshal`（反序列化解析器）当场就会因为语法错误而崩溃！这就是本实验的“核心死因”。
    

## 2. 幕后黑手：`"time"` (时间控制)

- **在 C++ 中**：你可能会用到 `<chrono>` 和 `<thread>` 里的 `std::this_thread::sleep_for()` 来让当前线程休眠。
    
- **在 Go 中**：`"time"` 包提供了所有与时间相关的操作，包括非常常用的 `time.Sleep()`。
    
- **作案手法**：在这个 `step3_sticky_packets` 实验里，`"time"` 包扮演了一个极其邪恶的角色。一会儿你会在服务端的代码里看到，我们在建立连接后，**故意调用了 `time.Sleep(1 * time.Second)` 让服务端“睡死”过去**。
    
    - 为什么这么做？因为我们要给客户端争取时间！
        
    - 在这 1 秒钟里，客户端会像机关枪一样疯狂调用 `Write` 把三个 JSON 包塞进网线。
        
    - 由于服务端正在睡觉，不去调用 `Read` 抽水，这三个包就会在操作系统的底层 TCP 接收缓冲区里**发生物理堆积，首尾相连**。等服务端 1 秒后醒来去 `Read` 时，拿到的就是一个极其恐怖的“连体婴儿”数据！
