
假设现在有两个玩家（客户端 A 和客户端 B）想同时连接这个服务器。

1. 客户端 A 先连接成功，服务端进入了 `handleConnection(connA)` 的死循环里，开始等 A 说话。
    
2. 此时，客户端 B 也运行了 `net.Dial` 想要连接服务器。
    

**你觉得此时客户端 B 能正常收到服务器的回执吗？为什么？** _(提示：在 C++ 单线程模型下，如果一个线程陷进了一个 while(true) 的 recv 阻塞里，外层负责 accept 的代码还能执行吗？)_

你可以先在大脑里“编译运行”一下，或者自己开两个终端实际跑跑看。告诉我你的结论和分析，然后我们再引出 Go 语言真正的“屠龙之术”——**Goroutine**！


# 解答


## 1. 为什么 B 收不到回执？(阻塞 I/O 的原罪)

整个 Go 程序实际上只运行在一个“主协程”中（你可以直接把它等价于 C++ 的 Main Thread）。

当客户端 A 成功接入后，执行流是这样的 ：

1. 主线程从 `listener.Accept()` 拿到 A 的套接字。
    
2. 主线程跳入 `handleConnection(connA)` 函数。
    
3. 遭遇 `conn.Read(buffer)`。在默认情况下，这是一个**同步阻塞调用 (Blocking I/O)**。
    

这意味着，只要客户端 A 不敲击键盘发送数据，服务器的主线程就会被死死“钉”在这个 `Read` 上，挂起并交出 CPU 执行权。**既然主线程被困在了内层的死循环里，它就永远无法回到外层循环去执行下一次 `listener.Accept()`。**

**极客底层补充**： 如果你此时用抓包工具看，客户端 B 的底层 TCP 三次握手其实是**成功**的！因为 TCP 握手是由 Linux/Windows 操作系统的**内核网络栈**自动完成的，完成握手的连接会被放在监听套接字的 `backlog` 队列中。但是，由于我们的应用程序层（Go 代码）没有去调用 `Accept()` 把这个新连接的 Socket FD（文件描述符）从队列里捞出来，客户端 B 发送的所有数据只会静静地堆积在服务器系统内核的 TCP 接收缓冲区里，永远等不到应用程序的回应。

## 2. 破局之道：C++ vs Go 的并发哲学

要想解决这个问题，让 A 和 B 能同时和服务器聊天，我们就必须引入并发。

**在 C++ 中你会怎么做？** 你大概率会每收到一个连接，就新开一个线程，或者扔进线程池：


```c
// C++ 的经典多线程处理方式
while(true) {
    int client_fd = accept(listen_fd, ...);
    std::thread(handleConnection, client_fd).detach(); 
}
```

但你肯定知道，OS 级别的线程（`std::thread`）是很“重”的：每个线程默认要分配兆级别（MB）的内核栈空间，而且 **OS 线程的上下文切换（Context Switch）需要陷入内核态**，开销极大。如果是上万人同时在线的网游，C++ 传统的“每连接一线程”模型会直接把服务器内存撑爆。

**在 Go 中怎么做？（屠龙之术的起手式）** 在这门课的第三章《英雄集结》中提到，为了把单机性能压榨到极致，我们抛弃了 OS 线程，转而使用 Go 的核心武器：


```go
for {
    conn, err := listener.Accept()
    // ...
    go handleConnection(conn) // <-- 仅仅加了一个 'go' 关键字！
}
```

这就是 **Goroutine（协程）**。

- **极度轻量**：一个 Goroutine 的初始栈只有区区 2KB（是 C++ 线程的千分之一），创建成千上万个 Goroutine 就像喝水一样简单。这使得“**每连接一协程**”的架构模式在资源消耗上成为可能。
    
- **用户态调度**：Goroutine 是由 Go Runtime 在用户态调度的，不需要频繁切换到内核态 。
    

当我们加上 `go` 关键字后，主线程在踢出 `go handleConnection(conn)` 后，会**瞬间不回头地**继续执行下一次 `listener.Accept()`，随时准备迎接客户端 B 的到来。
